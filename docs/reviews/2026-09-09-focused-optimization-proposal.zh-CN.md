# Codetrap 下一轮优化建议

日期：2026-09-09，America/Los_Angeles。依据：基线 `b9d680e`、此前产品检查、历史案例核验，以及开启原生记忆后的探索性测试。以下三批改动已按用户授权实现并完成本地验证；两个客户端的本机 Skill 已同步，用户已授权提交并推送源码。公开版本发布是独立步骤；结果见[实施交接](../tasks/2026-09-09-focused-experience/handoff.md)。

## 当前判断

保留现有 Bun/TypeScript、SQLite、CLI/MCP、候选审核与 Learning 架构，进行小范围优化。没有足够证据支持推倒重写，也没有证据支持继续扩展通用记忆平台。

探索性测试表明，在明确要求检查交付状态的任务中，不使用 Codetrap 也能完成主要检查。它没有测出 Codetrap 的额外收益，也没有证明原生记忆已经稳定解决所有项目经验复用问题。不要根据这一次检查直接否定整个产品，更不能宣称已经验证差异化优势。

下一轮验证的产品方向：让用户低成本保存少量有依据的项目经验，清楚知道何时适用、后来怎样被使用，以及何时需要修正。这是待验证的用户价值，不是已经建立的竞争壁垒。

## 第一批改动：修复检索结果的消费顺序

基线 `b9d680e` 中，`TrapStore.search` 按作用域检索，`limitAcrossScopes` 截取后重新保留分组，`toTrapActionCards` 直接展开分组。受控复现中，三条 project 结果分数为 0.4，一条 global 结果分数为 1.0，但全局结果排第四；Skill 又要求先看前三条。本轮已用统一消费排序修复，并覆盖总数不足 limit 的情况。

实现方向：为 Agent 的行动卡建立明确的统一排序约定；界面可以按作用域分组，但不能让展示分组决定 Agent 的阅读优先级。CLI、MCP 和 Observation 中的 rank 应一致。

验收：

- 既有语义检索复现中的全局高相关结果进入正确位置。
- 返回数量小于 limit 时，也遵守排序约定。
- 总数量限制、同分顺序及项目/全局同号记录仍然正确。
- FTS、semantic、hybrid 以及降级混用有明确比较规则；不能假定不同语料或不同检索模式的原始分数可直接相加或比较。
- 一次修复只补充相关边界测试，不重新建立一套 benchmark 平台。

主要入口：`src/lib/store.ts`、`src/lib/search-result-card.ts`，以及它们的 CLI/MCP 消费者和排序测试。

## 第二批改动：让用户完成第一条真实经验的保存

复用 Learning 已有的 AI handoff 能力，在 Review 和 Library 首次空状态提供“记住刚才这条纠正”的入口。区别首次空库与搜索没有结果，不要求用户先了解 session、candidate 或数据库字段。

预期路径：

> 用户表达一次真实纠正 → AI 整理短候选 → 用户查看原始依据和适用条件 → 保存或跳过。

默认保留简洁的正常操作；冲突、替换等处理在出现对应情况时展示。不要为通用常识和一次性讨论批量生成待审核记录，用户明确要求保存的内容按其意图处理。

验收：一名初次使用者能从空页面找到开始入口，完成一条本人经验的候选与确认，不需要作者逐步解释。用已有数据结构和接入方式实现，先不增加新的后端流程。

## 第三批改动：让单条经验的依据和使用结果可读

代码已有来源证据、修订、归档、反馈和 Observation。优先将这些内容在经验详情中串起来，复用现有详情及 Impact 入口。

用户应容易回答四个问题：

1. 这条经验源自哪次问题，依据是什么？
2. 在什么项目、路径或条件下适用？
3. 后来哪些任务检索过它，有没有使用与验证记录？
4. 如果它不准确或已过时，如何纠正或停用？

显示实际可证明的状态：检索/曝光、采用的报告、验证结果和用户反馈分别表达；缺少数据时显示未记录或未验证。AI 自报采用不能自动算用户确认有帮助；任务通过不能自动算这条经验阻止了错误。

调整 Skill 报告示例，优先写“检索到什么、实际采取了什么动作、验证结果是什么”。避免将“我本来会犯错”式反事实叙述当作效果证据。

验收：从一条经验能跳到相关任务依据，并能区分不同来源的判断；未知结果不显示成收益。若当前数据不足以支撑某种状态，本轮先如实展示缺失，不搭建大型自动归因系统。

## Learning 的范围

保留文章讲解、HTML/SVG 课程、学习内容检索等现有能力。用户可以只学习，是否转成经验由用户决定。Learning 的使用价值独立验证，不以转入经验库数量衡量学习是否成功。

这轮先把已有学习体验保持稳定，不扩展通用课程平台或为了配合经验库而强制转换内容。

## 第一轮开发的边界与后续验证

建议第一轮只交付：排序修复、Review/Library 首次入口、经验详情中的证据与使用记录汇总。保留已有后端和界面结构，不进行框架迁移，也不增加 Skill 数量。

之后邀请 3–5 位带有真实项目的开发者，各从 1–3 条确有依据的经验开始试用。观察他们能否独立开始、是否遇到后续复用机会、经验是否改变实际行动，以及审核与无关提醒造成的负担。小样本用于发现阻碍，不用于宣称市场已经验证。

对出现明确复用机会的任务，再比较原生记忆/项目指导与相同条件增加 Codetrap。保存数量、检索次数和模型自报成功不作为主要收益指标。没有出现复用机会与出现机会但未帮助，应分开记录。

暂缓：原生记忆内部文件的自动改写或双向同步、全面历史自动采集、更换向量数据库、复杂团队协作、经验市场和专门为本次两个检查题搭建的自动评测平台。只有实际使用问题要求时，再将其中某项列入开发。
