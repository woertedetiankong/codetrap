# 历史读取性能验证

测量日期：2026-09-05，America/Los_Angeles。Bun 1.3.13，macOS arm64。
这是一组临时合成数据，不能用作真实用户成长或任务收益证据。

每个任务包含启动、搜索、经验展示、验证、反馈和结束六条事件。
以 `f763195` 的 Ledger 实现为基线，在同一台机器顺序运行；每个读取
先测首次调用，再取五次重复调用的中位数。每次都重新打开只读连接。
测量范围是 Ledger 总览 + 最近 100 个任务，不包含浏览器渲染、网络或
客户端配置检查。原始值见 [performance-results.json](performance-results.json)。

| 任务数 / 事件数 | 基线重复读取 | 优化后重复读取 |
|---|---:|---:|
| 100 / 600 | 8.06 ms | 0.47 ms |
| 1,000 / 6,000 | 38.17 ms | 0.46 ms |
| 10,000 / 60,000 | 391.99 ms | 0.48 ms |

优化使用有上限的进程缓存保留计算结果：主文件、WAL 或回滚日志的身份、
大小、修改时间或变更时间变化后会重新读取。缓存最大 8 MiB、24 项，
单项超过 4 MiB 时跳过缓存；只保存投影，不保留数据库连接或完整事件。
数据库 schema 检查仍在使用缓存之前执行。返回副本避免调用方修改缓存。
最近任务的事件读取从逐任务查询改为两次批量查询，仍保持原排序和数量。

首次打开或新增事件后仍需扫描历史。1 万任务的总览首次读取约 375 ms，
最近任务约 25 ms；独立的连续追加实验中，刷新中位数约 396 ms。
因此，这次收益主要来自历史不变时的轮询和返回页面，不能解读成所有
读取都只需 0.5 ms。更大规模、持续高频写入时仍应重新测量。

验证覆盖：只读投影与完整重建一致、返回值被修改后缓存仍正确、其他进程
写入 WAL 后可见、schema 升级/文件替换、读取期间文件变化，以及未知
文件状态时绕过缓存。缓存不改变观测的启用方式。

复现：`bun run benchmarks/observation-refresh.ts`。比较旧版本时可使用
`CODETRAP_BENCH_LEDGER=/absolute/path/to/baseline-module.ts` 指定旧模块。
